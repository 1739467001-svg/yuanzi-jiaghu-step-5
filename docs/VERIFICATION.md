## 本轮 soak 发现并修复的两个真实缺陷

1. **soak 客户端重连缺陷（测试脚本）**：重连定时器与主循环会各建一条 WebSocket、旧 socket 不关闭，orphan 连接滚雪球——首轮 2 小时跑到 48 分钟时客户端连接数归零、服务端残留 512 条 ESTABLISHED 连接、重连计数 10,573。已改为单触发重连（已在连接/已连接时直接返回并显式关闭旧 socket）；修复后同样负载重连计数降至 29（5 分钟口径）。
2. **服务端缺少未认证连接超时（产品缺陷）**：只连不发 hello 的连接会永久留在 `connections`，既占连接又拖慢每 tick 广播。已在 `server/world.mjs` 增加 15 秒 hello 超时（`createWorld({helloTimeoutMs})` 可配，默认 15000），并有单测覆盖（未认证连接超时被 4008 断开、已认证连接不受影响）。

## 复跑确认（最新代码，30 分钟）

首轮 2 小时轮因端口残留打在了旧代码服务上（共坐功能代码相同，证据有效；内存指标丢失）。已加固脚本：spawn 的服务端进程退出即快速失败（端口被占时不再静默打到旧服务），且内存采样失败会显式断言失败。复跑 `ATOM_SOAK_MINUTES=30 ATOM_SOAK_PLAYERS=24`：161 次入座 / 141 次起身 / 97 次同桌相邀、座位不变量零违例、快照 p95 118.3ms、**服务端内存 54.3MB → 45.3MB（-9.1MB，有界）**、零页面错误。

PRD 的 72 小时压测仍未执行（本机环境不适合连续 3 天独占）。运行方式已固化：`npm run soak:72h`（即 `ATOM_SOAK_MINUTES=4320 ATOM_SOAK_PLAYERS=24`），报告每 30 秒增量写入 `artifacts/soak-report.json`，中途崩溃不丢数据；建议在专用低负载机器上执行。两小时轮的完整数据见 `artifacts/soak-report.json`。

# 2026-10-03 稀有微雨事件 + 画面精简（阶段 30）

## 稀有微雨事件

山上偶尔会落一场微雨，是稀有事件而不是常态天气：每 90 秒掷一次（8% 概率起一场），一场约 5 分钟后自己停。下雨时少侠与 AI 侠客都走得更慢、驻足更久，看雨里的人慢下来是这个事件的目的。

实现要点：`src/world/ambience.js` 的 `createRain` 提供斜落雨丝与脚下水洼光斑；引擎 `setWeather`/`raining` 只影响速度与等待；`App.jsx` 内置调度器与 HUD 指示（微雨图标 +「山色空蒙 · 微雨」）。本地世界与联机世界共用同一套接入。

# 2026-10-03 门派空间不再透出小镇的户外景（阶段 31）

## 问题审核结论

反馈：门派里还能看见飞鸟和远处的山，不合逻辑。审核确认问题属实，且不止一处：

1. **小镇远山挂在了场景级**（`createMountains(scene,…)`），门派内景、门派大殿、展示馆三个场景都共用同一份——进了门照样看见村口那座公共远山。
2. **夜空同理**：星星、月亮、月晕、流萤都是场景级，门派空间也在显示。
3. **飞鸟已在上一轮画面精简中删除**，反馈里提到的飞鸟问题实际已不存在（当时未同步说明，这里补记）。

实测证据（门派内景 1440×900 截图，容差 12 像素计数）：小镇远山三层色共 **12,850 个像素**、天色 69,330 个；前后截图按行带对比，y 120-180（远山所在背景带）差异 60%，而院落本体（y 240 以下）差异 0%——背景被换掉、院落分毫未动。

## 修法

原则：**户外景只属于户外空间**。门派内景与门派大殿不再挂小镇那座公共远山，改用场景自己生成的一圈主题色群山（`ambience.js` `createRidge`，远近两层共 52 座，配色由门派主题推算：远层淡、近层沉，夜里整体降一档；黛蓝与朱砂主题山色不同）。夜空的星星/月亮/月晕/流萤同样只在室外出现。本地世界与联机世界同一口径（两处并行修改）。

## 模型来源与转换

用的是放在项目目录下的 `原子侠_标准模型_八视图精修版.blend`（26MB，zstd 压缩，解开 50MB；Blender 5.0 版本号 050、8 台相机对应八视图、15 个材质、35 个网格对象：汉服白袍、交领袖口、腰带衣带、护腕绑手、白靴、斗笠、剑柄剑鞘、头眉眼嘴腮红）。本机没有 Blender，写了 `scripts/blend-to-glb.mjs` 直接解析 .blend 二进制输出 glTF。

解析过程中踩实了几个坑（都已写进脚本注释）：块头是 32 字节且 `len` 在 +16、`SDNAnr` 在 +4（不是标准 24 字节头的排布）；DNA 的 NAME/TYPE 字符串数组内部不逐条对齐、只在数组末尾补到 4 的倍数；TLEN 段没有计数字段；指针字段按 8 字节算、且 `name[258]` 这类名字要把整个 `[N]` 后缀去掉再作键。**Blender 4.1+ 的几何不走 mvert/mpoly/mloop 指针（全是 0）**，而在 Mesh 块之后紧跟的 `[属性名][数据][描述符]` 三元组里：`position` 是每顶点 3 个 float，`.corner_vert` 是每个角点一个 int 顶点索引，再往后一个 `(totpoly+1)` 个 int 的数组就是多边形环起点（首值 0、末值 totloop）。法线 MVert 里没有，用三角形面法线累积生成。

导出后的处理：顶点网格聚类抽稀（135 万 → 3.35 万三角形）、按身高归一到 1.7 米、按部件名上色（固色在着色器节点树里，`Material.r/g/b` 全空，而对象名本身就是美术给的语义：Douli/袍/带/腕/鞘/金/发/肤）。最终 527KB。

## 自测与验收

- three.js GLTFLoader 能解析（两个教训：`bufferView.buffer` 必须显式写 0，three 会把它当索引用；JSON 里出现 `null` 说明 min/max 被 NaN/Infinity 污染）。

## 已知边界（诚实说明）

- 该模型**没有骨架和动画**，行走/待机走 GLB 根节点兜底动画（起伏与转向），不会有摆臂迈步；要真正的走路需要 Blender 里补骨架并导出 idle/walk，接入逻辑不用改（`createAnimator` 按名字认）。

# 2026-10-03 程序化骨架与 idle/walk 动画（阶段 33）

## 做法

不想再回 Blender 摆骨骼，于是让转换器直接按 glTF 2.0 皮肤规范生成 rig：

- **骨架**（`scripts/skeleton.mjs`）：17 根骨， hips → spine → chest → neck → head，chest 分肩 → 前臂 → 手（左右），hips 分大腿 → 小腿 → 脚（左右）。层级指针在生成时就算好，骨骼节点作为 glTF 节点树插进场景，网格节点挂 skin。
- **权重**：双通道——部件名（头/袖/腰带/斗笠…）优先，未命中按身高分段（0.25/0.42/0.62/0.78/0.95/1.12/1.26/1.31 八个区间，相邻两骨按高度线性混合）。汉服下摆遮腿，所以袍子整体按高度分段，行走时下摆自然摆动。
- **动画**：walk 0.92 秒一个周期两步（大腿 ±0.42rad、小腿屈伸、躯干反向旋转、袖臂反摆、髋部升降 1.8cm），idle 4.4 秒（呼吸、轻摆、偶尔张望）。每个采样器用自己的帧数（≠ 第一个关节的帧数，这是踩过的坑）。

## 验证（Node 里用 three 的 GLTFLoader 加载）

| 检查 | 结果 |
| --- | --- |
| SkinnedMesh / 关节数 | 17，boneInverses 与 rest 世界矩阵互逆（误差 0） |
| rest 蒙皮偏差 | **0.000mm** —— bind 正确，静止时网格不被带偏 |
| walk 顶点形变 | 最大 4.1cm（头部网格），肢体与袍摆都在动 |
| idle 顶点形变 | 最大 1.4cm |
| 浏览器实测 | 帧间差异 37355 像素集中在角色区；让角色走起来后差异显著增大；无页面异常 |

## 三个真 bug（都被验证当场抓住）

1. **glTF 指定序列是列主序**，我按行主序写 `inverseBindMatrices` 会让蒙皮整体错乱。改为写前行主序、落盘转置。
2. **动画采样器要引用 accessor 下标**，不是 bufferView 下标——三个会当作索引查 `bufferViews[undefined]`。
3. **缓冲区估算写爆**：蒙皮+动画把位置/法线/索引之外又加了每顶点 32 字节，超出 `Buffer.alloc` 预估值，`Buffer.copy` 越界是**静默截断**——改成了按需翻倍增长。

另外蒙皮循环读错也骗过一次：我按 17 根骨遍历去读 `skinWeight`，而权重是每顶点 4 槽的 VEC4，等于把相邻顶点的权重读了进来，得出"权重和=5"的假结论。

## 顺带优化

`JOINTS_0` 从 float 改无符号字节（关节只有 17 个，1 字节就够），每顶点省 12 字节。
