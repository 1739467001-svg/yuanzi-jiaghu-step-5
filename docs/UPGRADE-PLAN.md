# 原子江湖 · 下一步功能升级方案

> **两份方案的融合版**：麦特哥《门派小镇 · 3D 创作工坊功能说明（重构版）》 × 我方《小镇重构思》（docs/TOWN-VISION.md）。
> 结论先行：两份方案不冲突，是**「院子」与「各家院落」**的关系——我方小镇是共享村落（原子门派大殿所在地），麦特哥的门派小镇是每个门派自己的 3D 家园；地形、素材、氛围、性能分级全部共用。主线是**门派小镇（创作工坊）**，我方小镇重构思作为它的资产与视觉基线并行推进。

## 0. 决策记录（2026-09-30 评审通过）

1. **建筑不做「构造/搭建」，只做「预设可更换」**：掌门从预设库里选地形、建筑组合、门派元素与主题色，不做拖放造景、不做自由地形编辑。编辑态从「搭建工具」降为「配置面板」——桌面与手机都是点选，交互风险和开发量都大幅下降。
2. **若预设更换实现成本仍高，先暂停门派小镇，转去做其他功能完善**（拟真水景与生态、桃花氛围、尺度拔高等不依赖编辑器决策的部分），掌门工坊随后续讨论再启。
3. **技术栈与三个取舍（地形五选一、分端交互、数据权威边界）审核通过**，按此开工。

落地顺序不变：M0（概念层 + 双向入口 + `?sect=` 深链 + 视觉统一）→ 资产批（并行）→ M1（预设配置 + 预览发布 + 分享 + 游客申请占位）→ M2 社交 → M3 权益。

## 3. 融合方案

### 3.1 主线：门派小镇（M0 → M3）

**架构决定**：门派小镇 = 用我方小镇的场景资产，按门派的「地形 + 建筑 + 元素 + 成员 + 碑」配置生成的一座**可编辑家园**。不是重做一个沙盒，而是把现有 `sectScene.js` 的固定内景升级为「模板 + 布局配置」驱动的可编辑小镇。编辑态（俯视拖放）与漫游态（第三人称）共用同一份布局数据。

- **M0 概念层统一**（约 1 轮）：内景首屏一张「这是什么」的关系卡（门派卡↔小镇↔官网三角关系）；补「返回门派大厅/返回官网」入口；视觉走查（字体与色板对齐他的规范）。
- **M1 MVP 单镇搭建**（约 2—3 轮）：默认模板（村落地形 + 议事堂 + 匾额 + 旗帜 + 主题色）起步；编辑态俯视 + 拖放摆放（建筑/元素/成员/碑四类先上，地形先做 5 选 1 的预设切换）；Ctrl+Z、可折叠素材侧栏、发布前预览；**发布后生成 `?sect=<id>` 分享链接**；未登录游客可浏览并看到「申请加入」入口（先落表单占位）。
- **M2 社交化**（约 2 轮）：成员入住（弟子/长老的化身进驻小镇、Agent 伙伴驻守）；游客拜访计数与足迹；申请加入的流转（游客提交 → 掌门/长老在后台处理 → 成为弟子自动入驻）；与官网门派数据同源（接 `ATOM_SECTS_SOURCE` 后成员/公告/标签以官网为准）。
- **M3 权益闭环**（依赖官网接口）：Token 碑、OPC 权益展示、共筑贡献记录、邀请赠金入口。

### 3.2 并行：原子江湖小镇重构思（我方 TOWN-VISION 压缩版）

水面平面反射 + 波动、拱券石桥、锦鲤/青蛙/蝌蚪/蜻蜓、桃花飘落与桃园结义碑、河中桃花岛、远山剪影、建筑拔高（地面 39×31→48×38，总高 6.5—9）、垂柳芦苇与飞鸟香烟招幡（已上线）。

**与门派小镇的融合点（这是两份方案咬合最紧的地方）**：他要的五种地形，正好由我方资产拼出来——

| 他的地形 | 用我方什么实现 |
| --- | --- |
| 湖畔 | 反射水面 + 拱桥 + 锦鲤 + 垂柳（拟真升级批的产物） |
| 林间 | 桃林/树冠 + 飘落花瓣 + 飞鸟（氛围批的产物） |
| 山地 | 远山剪影 + 坡地（尺度批的产物） |
| 村落 | 现有 atom-town 本体 |
| 浮岛 | 新增地形：把地面改成若干浮空台地（新做，量小） |

门派样式四套主题色板收敛为「朱砂 / 墨绿 / 茶褐 / 黛蓝」四套低饱和色，同时服务门派大殿着色与他的「主题色」维度。

### 3.3 视觉与交互统一（贯穿两条线）

1. 正文字体 DM Sans → **Noto Sans SC**（与主站一致）；
2. 侠客默认衣带色去掉科技蓝，默认改朱砂/墨绿；
3. 编辑态俯视 + 拖放，漫游态第三人称；Ctrl+Z 回退；可折叠素材侧栏不遮挡 3D 主视图；
4. 一键回主站：内景右上角常驻「返回门派大厅 / 返回官网」；
5. 性能分级沿用现有策略（手机端粒子减半、反射降级），每批用 `audit:mobile` 与 e2e 复核。

## 4. 技术对接点（都可以直接落到现有代码）

**数据模型映射**（官网门派卡 ↔ 我方门派 ↔ 小镇元素）：

| 官网门派卡 | 我方 `server/sects.mjs` | 小镇元素（新增表） |
| --- | --- | --- |
| name / slogan / tags | name / slogan / intro | 匾额文本、旗帜图案 |
| 开放加入 / 邀请制 | （待加 `joinPolicy` 字段） | 门口石碑状态 |
| members[] | elders / disciples | 成员雕像与驻守位置 |
| 权益（Token/OPC） | （待加 `benefits[]`） | 权益碑与展示柜 |
| logo / 主题色 | style | 门派元素配色 |
| 公告 | （待加 `notices[]`） | 公告牌 |

**入口与深链**：新增 `?sect=<id>` 路由（完全复制 `?work=` 的实现：解析 → 定位到门派大殿 → 打开该门派内景），配合右上角返回入口与分享按钮，满足他的入口路径三条。

**权限扩展**：在现有 `assertFounder()`（仅创始人）之上加三档——
- 长老：`canEditElements`（协助布置）、`canNotice`（代管公告）；
- 弟子：`canContribute`（共筑：提交素材建议/点赞，掌门审核后生效）；
- 游客：只读 + 申请加入。
所有权限判定仍在服务端（与现有会话令牌一致），客户端只做界面呈现。

**服务端草稿与发布**：小镇布局作为门派的 `townLayout` 字段，**未发布时为本地草稿**（覆盖层，与门派同步的草稿槽位分开），发布后写入门派数据；官网为权威时，布局字段随门派一起同步，冲突以发布时间戳为准。

## 6. 待确认问题

**他的四个待确认，我先按现有代码回答：**

1. **原型访问不到**：我们这边预览地址是 `http://127.0.0.1:5173`（本地）与 GitHub 仓库 `yuanzi-jiaghu-step-5`；四层断裂的诊断可以拿这个跑一遍逐条核对——其中「视觉断裂」「移动端」「子站割裂」三条我们这边已经不成立（见 2.1），真正要修的是概念、入口、玩法、权限、价值五条（见 2.2）。
2. **技术栈**：不需要新子站——门派小镇在原子江湖同一个 React + Vite + Three.js 单页里，复用全部场景资源（地形/建筑/元素/氛围/特效模块都是现成的）。
3. **数据模型**：映射表见第 4 节；官网是权威源这一点，我们的 `sects-source` 已经是「外部权威 + 本地覆盖层」结构，接上即可。
4. **设备范围**：移动端已覆盖并有 5 档视口体验门槛（无重叠/无溢出/触控目标 ≥24px），低端降级策略已分级。

**需要你和麦特哥一起拍板的：**

1. 官网门派大厅的**接入方式**：是给我们 API（读成员/公告/权益）+ 深链回主站，还是我们先按 `ATOM_SECTS_SOURCE` 的契约对接？（决定 M2 的排期）
2. **M1 的最小集范围**：六个维度里地形先做「五选一切换」（不做自由造地形）可以吗？建筑先做「模板库拖放」（议事堂/演武场/藏书阁三件套）可以吗？
3. **Token / OPC 权益系统**是否有可读接口？没有的话 M3 先用静态展示占位。
4. 门派小镇要不要**独立域名/入口**（比如 sects.atomclub.cn），还是继续嵌在主站江湖里？
5. 麦特哥文档里的「Agent 伙伴驻守」——是指我们现有的八位 AI 侠客进驻门派小镇，还是每个门派可以有自己命名的 Agent 伙伴？
